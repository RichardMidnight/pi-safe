pisafe — test plan and status (as of 2026-10-23)
=====================================================================

1. What is being tested
---------------------------------------------------------------------
pisafe (script under test: 1.2.12-beta.6 across the fleet) and the
test harness (pisafe_test, v2.0-v2.2). Each battery run exercises:

  - backup in 4 arms     : zip, gz, xz, zst (dd + pishrink shrink + compress)
  - restore in 4 arms    : zip, gz, xz, zst (uncompress + pishrink expand + dd)
  - 4 erase/confirm steps between arms
  - 12 steps total per run

Per-step contract (harness):
  PASS = pisafe exits 0 AND a fresh pisafe-log window after the step's
         seed point contains the step's success marker AND no failure
         line (FAIL_RE) appears.
  FAIL = anything else; the record then shows exit status, and — when a
         pisafe error line matched — a log-window dump.

Battery-level properties also under test:
  - dependency install: pisafe must install missing tools on the box
    (harness auto-approves that one prompt; the step's record must then
    prove the install actually worked)
  - failure handling: a failed step must be caught with a usable reason,
    the card must not be left half-written, and the remainder of the
    battery must still complete
  - setup mode (v2.1): one-file bootstrap of the pair from GitHub
  - report capture: report block on screen + saved to
    <CWD>/pisafe_test-report.txt


2. What must be covered (the matrix)
---------------------------------------------------------------------
  a) package-manager family (pisafe's installer speaks apt, pacman, dnf)
       apt    — Debian / Raspberry Pi OS / Ubuntu / Mint / DietPi
       pacman — Manjaro (ARM)
       dnf    — Fedora-family          [NONE YET]
  b) architecture
       aarch64 — most fleet boxes
       x86_64  — laptop boxes
       armv7l  — 32-bit userland       [none of the "32"-named boxes was
                                        real 32-bit until buster]
  c) distro age
       current (trixie) through EOL (buster) — tests the installer's
       behavior when repos still work and when they no longer do
  d) GUI vs headless
       headless/minimal proven (trixie-lite)
       desktop boxes carry whiptail/newt; the battery itself runs CLI
  e) harness features
       v2.1: setup mode, one-`y` dependency auto-approve, report saving
       v2.2: pre-battery native-surface capture in the report (TUI
             backend, installer family, `which`, terminal +
             x-terminal-emulator target, editor, sound, EUID) —
             read-only (`command -v` only, no installs); this is what
             fills the TERMINAL/EDITOR cells of section 4
       env mode (in the v2.2 build, added 10-23, not yet committed):
             the `env` subcommand prints the same machine header +
             surface block on demand: no battery, no device, nothing
             installed, nothing read from stdin. Share-safe by
             construction — it is read-only, and the LMDE and noble
             captures ran it straight off the SMB gvfs path. The
             log's four ENV blocks are its output.
  f) interactive surface (install footprint, TUI, text editor,
     terminal, `which`)
       the battery runs CLI flags only — the install footprint (CLI
       script, icon, desktop entry), the whiptail/newt menus, the
       editor chain, the terminal chain and the `which` primitive that
       every install check depends on are never exercised by it; each
       needs one confirmed manual pass per box (see the checklist)
  g) network
       every fleet box reaches a package repo; the fully-offline
       failure path is only observed on buster (dead EOL repos)
  h) card size
       fleet cards are small (the 4-GiB gz-footer edge is the only
       size-class known); a 64-128 GiB round trip is untested

8. Per-box interactive-surface checklist (manual, at a console)
---------------------------------------------------------------------
  The battery cannot prove any of this; someone with the box can, in
  a few minutes at a console. Record each line under the box's entry in
  testing/pisafe_test_log.txt. Status column: P = works, F = broken, ? = absent.
  Suggested order: the shape checks first (TUI, editor, terminal,
  which), then the install cycle, and uninstall last — the install
  cycle on one box per distro family is enough for the cycle itself;
  every box gets the shape checks.
    [ ] install   `pisafe install` (TUI: Install, or CLI) and check
                  every artifact it claims:
                    * script at /usr/local/bin/pisafe, and its `-v`
                      matches the version you ran (if the GitHub
                      fetch failed the running copy is installed
                      instead and a warning is printed)
                    * icon at /usr/share/pisafe/pisafe_icon.png
                      (a warning = default icon in the menu; note it)
                    * /usr/share/applications/PiSafe.desktop exists
                      and is syntactically a desktop entry
    [ ] menu      the entry is actually findable in the box's menu -
                  record the menu name and the icon shown, and that
                  selecting it opens a terminal window running the
                  whiptail TUI.  The install message says
                  'Accessories' but the entry's category is Utility;
                  where it lands depends on the desktop, so record the
                  fact, not the message.  Silent shape: a box with no
                  terminal emulator gets NoDisplay=true - install
                  reports success and the menu shows nothing; record
                  which shape the box has
    [ ] TUI       the whiptail menus load, open and navigate. Record
                  which renderer the box got: whiptail (installed by
                  pisafe) or the newt fallback (the box's installer
                  ran `newt` on fedora / `libnewt` on arch+manjaro
                  when whiptail could not be installed). Note: the
                  newt build has no --timeout, so the erase countdown
                  appears as a Yes/No gate instead of a ticking timer
                  - that is the intended behavior, not a defect
    [ ] which     the box can `which` (pisafe's env_which probes with
                  `which` and tries to `install which` on first use if
                  it is missing — note that apt + pacman + dnf attempts
                  all fire without checking the family first) and that
                  it resolves a known tool, e.g. `which dd`
    [ ] editor    pisafe's `settings` / `log` commands open the file in
                  the first editor it finds in its chain (leafpad, xed,
                  gedit, featherpad, kwrite, pluma, kate, mousepad,
                  geany, gnome-text-editor, nano); record which one
                  the box picked and that the file opens and saves back
    [ ] terminal  env_terminal locates one of: lxterminal,
                  xfce4-terminal, mate-terminal, gnome-terminal, xterm,
                  terminator, konsole, qterminal, x-terminal-emulator
                  (its symlink read resolves to the real one); record
                  which one, and that a pisafe terminal window actually
                  launches from the desktop path
    [ ] sound     the beeps need SOUND=on in the config and a working
                  speaker-test. Record the shape: beep heard, silent
                  with speaker-test present, or silent with it absent
                  (pisafe degrades to silence - the intended behavior,
                  but confirm the menu still works in that shape)
    [ ] update    at launch the update check fetches the main-branch
                  script and compares versions: record which path the
                  box took - the up-to-date message, the update
                  prompt (and its from/to versions), or the
                  'Can't connect to server' error with no install
                  attempted. Do not accept an update offer during a
                  battery window
    [ ] uninstall `pisafe uninstall` (TUI: Uninstall, or CLI) and
                  verify the reverse: script, icon, desktop entry and
                  config file all gone - and the log file is still
                  there (it is deliberately kept, and the message
                  says so)

9. How to run (one box, short recipe)
---------------------------------------------------------------------
  Flash the SD, boot the box:
    bash <pisafe_test> setup           # pulls the pair + creates the dir
  or, if the pair is already on the box:
    cd <pair-dir>
  Environment record only (no battery, no card, nothing installed):
    bash pisafe_test.sh env
  Run:
    bash pisafe_test.sh /dev/sdX -y       # erases the card at every step
  Output:
    report block on screen, plus <CWD>/pisafe_test-report.txt
  Append the report (or env) block, plus any manual notes, to testing/pisafe_test_log.txt.


10. Round note — gz sizing: refuse to make gz >= ~3.9 GiB; reader is uniform (2026-10-23)
-----------------------------------------------------
   Status: code done + agent-verified, UNCOMMITTED (no commit approved yet;
   on top of development@d8d5d47, where the working tree also carries the
   Pi-5 estimate-line change and the harness env-mode chunk — see section 7C).
   Supersedes the 10-19 handling (166f997 lineage: "restore measures/asks"),
   the same-day "just warn" pivot (unknown listings + no-total bar), and that
   day's intermediate "trust the footer, warn where it lies" state.

   Final direction (user decision, 2026-10-23): the sane way to deal with the
   32-bit size field is to refuse to make gz files whose estimate is over
   ~3.9 GiB.  Then gz image sizes work normally (the footer is exact by
   construction) and the code gets cleaner (one size path, no warning text).

Design:
    - creation side — refuses to make big gz, at both decision points:
        * pre-backup guard (media_backup_checklist, before any write):

Findings established during the fight (record):
    - the limit is in the gzip FORMAT, not pigz: the trailer ISIZE is the
      size mod 2^32 by spec; gzip and pigz write the same truncated
      trailer, so "make >4G files with gzip instead of pigz" doesn't
      work.  (Measured here: 5 GiB gzip -1 file; pigz -l on it ->
      residue 1073741824.)
    - twist (measured here, gzip 1.13 / pigz 2.8): INTACT 5 GiB gz —
      gzip -l says 5368709120 (the TRUE size) while pigz -l says
      1073741824 (residue); HALF-CUT copy — gzip -l fails ("unexpected
      end of file", rc 1) while pigz -l succeeds with garbage
      3235934264.  So gzip 1.13's -l is a full decode pass: true sizes
      at any scale (the rejected measurement cost minus the restore
      write), unverified on older fleet gazips.  Not adopted
      (version-dependent); it is the "something else" fallback if ever
      needed.
    - pigz 2.8 quirk: pigz -l SUCCEEDS (rc 0) on a truncated gz — the
      garbage number for incompressible data, the true one for
      compressible.  Trusted as-is; the gate then treats it like any
      numeric size.
    - the field box's wc -c is a 32-bit counter (7948206080 measured as
      3653238784 = size - 2^32); dd "N+P records out" from a pipe is racy.
